# 深度发现身份补证、人物合并与存量恢复方案

状态：设计方案，未实施。2026-10-13。用户要求只提供方案；本轮只写计划，不改业务代码、线上数据、发送配置。

历史名单的原始讨论见 [10,686 条历史数据处置方案](discovery-historical-data-disposition.md)。按用户最新范围，这份待确认名单仅保留为参考，不是本次处理目标；下文原 01—03 的存量步骤同样不得据此自动启动。

用户追加“同一人多个邮箱应合并为一个人”，并要求后续发现代码一并修正。本次新增 04—10 子计划，范围只限 **新发现（discovered）**：历史批次使用冻结名单，后续新数据必须由发现流程产生且当前带该标签。依据 [同人多邮箱审计](../../audits/2026-10-13-discovered-person-duplicates/report.md)，51,829 条中有 3,741 个高置信候选组、8,426 条档案，另 161 组待核。其他标签记录不迁移、不合并、不修改；可只读检查其历史关联以避免误合并。以下均为方案补充，尚未修复或合并。

## 需求描述

让已有可靠原文关系的专家获得身份证据和正确准入结论；让仍无法确认的记录保留具体原因。将“缺资料”“身份不明”“明确不合格”分开。

新增结果：同一可靠身份在专家列表只有一人，详情列出其多个邮箱；后续再次发现新邮箱归入此人；首封邀请按人选择一个合格邮箱，预估、实际目标及并发发送一致。历史原始档案作为邮箱证据和业务引用保留，不靠物理删除实现合并。

保持：业务主键、邮箱、人工决定、运营字段、联系人和邮件历史；来源唯一对应要求；原有下载预算和人工暂停。范围外：猜姓名、按邮箱拼写配作者、批量签发人工认可、自动发送、跨身份纠错、全面重写解析器和新建审核 UI。

## 关键不变量

### Invariant I-1：五个方向不是五个已量化的线上故障
- Rule：按用户可见问题归组为五项；存量回源和留痕是能力补齐，有限回退是策略调整。不能把历史 22 项全部列为当前未修复问题，不能承诺 5,547 人全部恢复。
- Applies to：实施范围、回放统计、最终报告。
- Violation consequence：重复开发已修功能，虚报恢复人数。
- 来源：本轮源码及历史名单核对。

### Invariant I-2：补证、准入、发信分别统计
- Rule：身份确认不能直接置 AUTO_PASSED；必须调用准入政策。方向/国家/机构缺失按另案软化，明确负面保留。邮件发送数始终为零。
- Applies to：所有子计划及存量执行。
- Violation consequence：把论文作者关系误报为最终可发送资格。
- 来源：K-enrichment-write-three-layers、既有准入方案。

### Invariant I-3：局部更新与人工保护
- Rule：真实 `_id` 不变，三层已有档案按版本条件局部更新；人工/历史认可按既有身份哈希规则保护。明确姓名、作者 ID 冲突不自动覆盖；姓名变更涉及旧学术字段或联系人时单列另案。
- Applies to：增量补证、存量应用。
- Violation consequence：身份误绑、跨层不一致、历史会话损坏。
- 来源：K-promotion-source-passthrough、K-expert-classification-one-object-three-layers。

### Invariant I-4：新发现范围与可靠合并
- Rule：历史应用必须同时命中冻结 discovered ID 和实时标签，且身份、版本未变；其他标签不纳入。稳定作者编号必须绑定当前姓名邮箱证据；仅同名、同机构、相似邮箱不能合并。161 个待核组不自动处理。遇范围外关联只报告冲突。
- Applies to：04/05 人物登记、06 查询、08/09 发送、10 历史应用。
- Violation consequence：同名误合并，或越过用户限定范围。
- 来源：用户最新指令、本轮审计。

### Invariant I-5：人物主档与邮箱事实分离
- Rule：人物关系以新增数据库登记为唯一来源；personId 稳定，主档关联多个原 docId/邮箱。旧 EMAIL-* 和 ORCID 形业务键不改名，邮箱仍独立保存来源、绑定证明、准入、验证、退信与抑制状态。现有 expert_email_alias 不充当未联系专家的人物表，不为合并虚建联系人。
- Applies to：04—10；三层 ES、V148 准入、联系人及历史邮件。
- Violation consequence：借一个合格邮箱放行所有地址，或破坏历史引用。
- 来源：V10/V23/V148、现有 ExpertProfile 单邮箱结构。

### Invariant I-6：所有专家列表先聚合后分页
- Rule：ES 专家列表及数据库联系人分支均按有效 personId 聚合后统计、排序、分页；范围外沿用原单位。筛选条件须由同一成员记录完整满足，不能把 A 的国家与 B 的领域拼成符合。按层级统计，RAW 的成员不能把人带入 CANDIDATE。详情保留来源成员与原 contactId 的入口。
- Applies to：06/07、列表总数、标签/地区/邮箱域名计数。
- Violation consequence：同人跨页重复、数量虚高、筛选或历史不可追溯。
- 来源：K-group-before-pagination、K-expert-detail-two-panel-render-sites（本轮已重新定位两个宿主）。

### Invariant I-7：首封按人且按具体邮箱审核
- Rule：先逐邮箱执行既有准入、显式筛选、抑制和验证，再每人选一个地址；同一人的人工 HOLD/REJECTED 或身份冲突不得通过另一邮箱绕过。显示主邮箱不等于发送许可。预估无写入；所有 INTRODUCTION 入口共享人物级原子占位，历史已发或结果未知均阻止自动换邮箱再次首发。
- Applies to：08/09；旧定时、新批量、失败重试、详情手动介绍邮件。
- Violation consequence：重复邀请或绕开人工拒绝。
- 来源：K-recipient-count-preview-parity、K-dual-outreach-paths，并补核 ManualExpertMailService 直接发送入口。

### Invariant I-8：失败可恢复，开启必须完整
- Rule：成员登记失败不算完整发现成功；关系失效/查询不全不返回伪造的人数。人物显示、目标选择、发送保护、历史映射准备均完成才开启总开关。已开启后回退 UI 不能撤掉首发保护；历史不明、SMTP 结果未知不得按超时重新首发。
- Applies to：05—10、发布和回滚。
- Violation consequence：修复后继续积累重复记录，或发布窗口重发。
- 来源：K-master-plan-shared-file-sequential-gates。

### 存储与写读路径

各子计划列出自己的完整路径。跨计划主链为：原文提取 → 三层身份补证 → 学术补全/准入重算 → 候选投影 → 原发送筛选。身份、准入、发送三者不能互相代替。

三层 ES `dynamic:false`，本组不新增 ES 字段；V131 学术任务按 expert_doc_id 唯一；V148 准入按真实 ID + identity_hash + revision；均复用原表。业务 `_id` 即使形似 ORCID 也不重命名。联系人和邮件表只读检查，不写入。

上段指原 01—03 补证计划；新增 04/09 单独新增人物关系表及首发保护表，不改现有共享表字段或 ES mapping。09 在今后的真实发送时保留原联系人、邮件写入流程；10 历史合并不改这些业务行。07 有前端改动，样式契约见该子计划。

知识只读加载；用户要求仅方案且知识文件已有其他改动，本轮不改 hit_count、不归档、不改 CLAUDE.md。K-dual-outreach-paths 关于旧路径“无 delay”的旧描述已与源码不符，本计划仅采用其双入口提醒，按当前源码保留 sleepBeforeNextSend。

## 实现方案

### 当前追加：新发现人物合并（04—10）

1. **04 建人物主档**：独立关系表连接原邮箱档案，可信作者键唯一。展示主档和具体发送邮箱分离；不删除 ES、联系人、邮件。
2. **05 修后续入口**：论文/ORCID/队列及重复补证共同登记；同人新邮箱增加联系方式，重跑不增人。并发冲突、跨范围、缺证据产生明确结果。
3. **06/07 修读路径和 UI**：按层级/筛选条件先归人后分页计数；两列表分支、两详情入口展示主档和邮箱。原 docId 链接仍可定位原邮箱及历史，业务操作不得暗中扩散到全部成员。
4. **08/09 修发送闭环**：一个人选一个合格地址；跨页/批次重试一致；数据库原子占位覆盖所有介绍邮件入口。历史发信/人工拒绝/未知结果保护优先于备用邮箱。
5. **10 历史处理**：将 51,829 条逐条分为合并候选、待核、保留、执行时变化；先 dry-run，再按独立执行授权应用 50 组试点。3,741 组是候选上限口径，不承诺全部直接合并；161 组不自动合并。主档关系落库，原记录零删除。

开发顺序：先验收既有准入修正及原 01/02 的补证接口代码，再 04 → 05 → 06 → 07 → 08 → 09 → 10。每个子计划单独验证。共享文件必须在前计划结果上继续：04 的 service/repository 由 10 复用；05 以原 01/02 已验收产物为补证接口基线，这些代码依赖不授权其旧待确认名单执行；08/09 依次修改 ManualInitialOutreachService、InitialOutreachService；06/07 的 API/DOM 契约联合验收。禁止从旧版本覆盖共享文件。

发布：04 可先部署空表；05—09 可在默认关闭的总开关下逐步部署和验证。10 在开关关闭且目标发现/首发入口暂停的维护窗口建立初始映射、导入历史首发保护，再追平增量；标签、身份证据和准入的目标写入同样暂停，保证名单复核与提交之间无竞争。所有目标被映射或明确隔离、交互及并发验收通过后才共同开启。维护结束恢复之前的运行配置；本轮仅记录此流程，不操作开关。SMTP 有未知结果则保留保护，不能用关闭开关回退为旧逐邮箱发送。

研究门禁：06 首版使用流式完整匹配集 + 批量人物映射精确聚合，避免新增 ES 冗余人物字段。上线前用真实规模测耗时/内存；若 5 万级数据不能达到子计划预算，先修订查询/投影子计划，不能以当前页去重或近似 cardinality 假充精确总数。跨存储标签/身份变化通过指纹复验及发送前复验限制；不声称 MySQL 与 ES 是同一事务。

### 原补证路线（保留设计，存量范围已收窄）

以下 200/50 抽样与 10,686 旧名单属于原方案背景。当前不启动其存量执行；若复用回源能力，只能传入本次 discovered 范围的 ID，不自动处理其他标签。

1. **先完成现有准入方案的规则/CAS/重验阶段**，避免补证成功后又被旧条件撤回。单独验证，不执行全量迁移。
2. **01 增量补证**：先使重复发现能够补回同身份证据，堵住后续积压入口。
3. **02 定向回源预览**：固定当前名单，先按来源与历史原因分层抽取 200 人（组不足则全取，记录真实分母）用当前解析器回放；证据充分的结果逐条核对。再全量只读预览，输出互斥结果及修改清单。
4. **03 有限回退**：在预览确认存在“首来源只有邮箱、备用来源能唯一绑定”的真实样本后实施；没有真实增益则不为凑修复点上线。为未解决样本增加解析规则必须另有原文复现和小计划。
5. **存量应用**：后续实施范围内先小批 50 人，再依结果扩大。应用只处理通过本方案条件的记录；断点恢复依据逐条结果，不重新清空队列。应用完再按既有准入方案重算并做发送预估，仍不发送。

研究检查点：200 人只用于发现模式，不外推全量成功率；5,547 人优先，不是承诺值。来源长期不可访问、共享邮箱歧义、冲突不得靠放宽身份门槛解决。

## 人工验收清单

### A-1：名单和证据
- 前置条件：隔离环境加载固定名单及按原始字节保存的样本，禁 SMTP。
- 操作步骤：运行 02 的预览；逐条打开来源及修改差异；对照原名单 ID。
- 预期结果：每个 ID 恰有一个最终处理结果；未核验不算通过；预览专家/准入/联系人/邮件写入均 0。
- 覆盖：I-1/I-2，R2/R4。

### A-2：增量与存量闭环
- 前置条件：同身份缺证一条、缺名且无学术/联系人一条、明确姓名冲突一条、来源不可得一条。
- 操作步骤：前一条走重复发现，第二条走定向恢复，后两条走预览；再执行准入重算和批量预估。
- 预期结果：前两条在原文关系唯一且无硬原因时进入相同准入链；后两条保留原档案和具体原因；新增专家 0、发信 0。
- 覆盖：I-2/I-3，R1/R2/R5及跨计划主链。

### A-3：保护和回滚
- 前置条件：人工 HOLD/REJECTED/LEGACY_APPROVED、已联系、有明确作者 ID 冲突、跨层不一致各一条；另模拟中途某层 409。
- 操作步骤：预览并应用；读取三层与原业务记录；用备份生成逐条回滚提案并检查当前版本。
- 预期结果：不得覆盖人工决定和旧身份；冲突记录不自动应用；部分成功单列且可续跑；联系人和邮件逐值不变；不删除已有档案；回滚提案不直接写生产。
- 覆盖：I-3及全部保持项。

### A-4：来源回退是否值得实施
- 前置条件：真实首来源未绑定、备用来源明确绑定的归档样本；另有全部来源歧义样本。
- 操作步骤：按 03 对比请求数、身份输出和耗时。
- 预期结果：前者新增可验证关系、后者仍不绑定；不突破单篇预算；如未证实收益，03 不计入已完成修复。
- 覆盖：I-1，R3。

### A-5：同人多邮箱完整闭环
- 前置条件：隔离环境禁真实 SMTP；导入 3 个不同邮箱、同一可信作者编号的 discovered 档案，以及同名不同编号、范围外各 1 条；前 3 条打散到不同 ES 页。
- 操作步骤：执行人物登记；打开新发现列表及任一邮箱的旧链接；运行发送预估；用假 SMTP 并发触发旧定时、新批量首发，再从详情尝试介绍邮件。
- 预期结果：3 条成为 1 人，详情显示 3 个独立状态邮箱；另 2 条不被合并；若这 3 邮箱均合格且无历史，预估 1 人，假 SMTP 总调用 1 次，邮件仍记录实际地址和原 docId。
- 覆盖：I-4— I-8、04—09。

### A-6：历史保护与后续不再重复
- 前置条件：测试库加载含历史邮件的一组和缺证据的一组；冻结新发现名单；准备一条应用前被移除标签的记录。
- 操作步骤：运行 10 的预览和小批应用；查看旧邮件；再发现已合并人物的第 3 个可信邮箱；重复执行同一批次；查看名单外档案。
- 预期结果：旧邮件/联系人值不变、旧链接可用；合并人物仍 1 人、邮箱增至 3；缺证据组保留独立；标签变化项跳过并记原因；重复应用新增成员 0；名单外写入 0、物理删除 0、实际邮件 0。
- 覆盖：I-4/I-5/I-7/I-8、10、后续发现入口。
