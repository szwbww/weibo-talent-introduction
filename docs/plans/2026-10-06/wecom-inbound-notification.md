# 专家来信企业微信群通知：开发方案

日期：2026-10-06。状态：待评审；本轮交付前端交互预览与方案，未修改生产代码、配置或发送群消息。

## 需求描述

在收发件箱顶部操作区、「自动回复」右侧增加「群消息 已关闭/已开启」开关。控制本系统向一个企业微信群推送新收到的已匹配专家来信，全局生效，默认关闭，保存后重启仍保留。

- 开关与自动回复独立；自动回复全部关闭时，仍可通知专家来信。
- 通知：专家姓名、发件邮箱、收件账号、主题、收信时间、最多 160 字纯文本摘要。第一版不发送完整正文、附件，不新增会话深链。
- 关闭期间不生成通知；重新开启不补发历史来信。已经提交给企业微信的请求无法撤回，关闭瞬间最多可能有一条在途通知。
- 保留：收信、IMAP 确认、自动回复、专家状态、标签、人工工单、批量发送、现有刷新按钮的行为。
- 不包含：多群配置、按专家订阅、通知日志页面、网页编辑 Webhook、短信、私聊机器人、部署上线、实际群测试。

## 关键不变量

- I-M1：开关的唯一事实源是 MySQL；前端本地状态不得替代服务端配置。
- I-M2：收到通知不等于已回复专家；通知开关不得写 `autoReply.globalEnabled` 或联系人自动回复字段。
- I-M3：本轮预览只模拟交互，无真实 API/Webhook 调用。真实凭据不进入方案、预览、前端资源或 Git。
- I-M4：实施分两步，每步独立验证；先完成后端，再接前端，后端首次发布保持关闭。

## 现状审计

- `index.html:794–804` 是目标面板；刷新按钮由 `mailbox-chat.js:870–887` 移入动作区首位，不是 HTML 中缺少刷新。
- `app.js:17994–18043` 为独立的全局自动回复控制；不适合直接复用其接口存通知状态。
- `AutoMailReplyService.processSingle` 使用事务包住核心处理，提交后才 markSeen；两处确认函数新建 `inbound_mail_processing`。自动回复全关分支仍保存来信。
- 系统有 MySQL JDBC、Flyway、定时任务及 MySQL Testcontainers 先例；无需新增 RabbitMQ 依赖。
- 详细读写路径、迁移、接口和样式事实见两份子方案。现有工作区包含其他未提交改动；实施应按清单隔离。

## 实现方案

1. [后端通知与持久化](wecom-inbound-notification-01-backend.md)：10 个文件；建立独立开关、持久化通知队列、异步发送、限速与有限重试。可先单独部署，默认关闭，API 可验证。
2. [前端开关](wecom-inbound-notification-02-ui.md)：4 个文件；实现截图位置的开关、加载/保存/失败状态、响应式布局。

部署配置只需 `WECOM_EXPERT_INBOUND_WEBHOOK`。配置是否存在由服务端返回布尔值；配置有效性最终须通过获授权的真实群联调确认。推送时效 = 现有收信轮询等待 + 处理时间 + 通知排队时间；此功能不会改变当前收信频率。

## 人工验收清单

### A-M1：完整体验
- 前置条件：两步已部署至测试环境，配置获授权的测试群 Webhook，手机企业微信开启该群通知。
- 操作步骤：打开收发件箱；开启群消息；由测试专家邮箱发送一封新信；执行「检查回复」；随后关闭再发第二封信。
- 预期结果：第一封信入库且群收到一条通知，第二封入库但群无新增通知；自动回复开关保持原值。再次开启不补第二封。
- 覆盖：全部需求、I-M1/I-M2/I-M4、S-1/S-2。

### A-M2：预览审阅
- 前置条件：打开本轮提供的可点击预览。
- 操作步骤：点击最右侧「群消息」两次，分别查看开与关。
- 预期结果：灰色关闭、蓝色开启，显示保存中反馈；其他按钮不变；不会向真实群发送消息。
- 覆盖：I-M3。
