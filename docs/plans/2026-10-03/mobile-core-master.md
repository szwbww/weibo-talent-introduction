# 手机端核心流程适配开发方案

日期：2026-10-03。状态：待用户审阅；本次只制定方案，未修改产品代码、未部署。

## 需求描述

在现有人才引进管理系统中，用手机完成查专家、阅读与人工回复邮件、查看会议、查看任务状态。这里沿用上一轮确认的管理系统范围，不涉及 qingfeitalent.com 品牌官网。

默认目标：360–430 CSS px 的竖屏手机、横屏及平板；验收 iOS Safari、Android Chrome。具体设备尚未指定，浏览器实际版本在执行时记录。主手机断点统一为 `max-width:760px`，761–1024px 保留现有平板规则，1025px 以上保留桌面分栏；补测 760/761、1024/1025 的边界。

必须保持：登录权限与退出行为、原页面入口、接口与业务字段、专家筛选分页、草稿隔离与发送目标、附件及会议数据语义、任务真实状态和轮询语义、桌面布局及个人分栏偏好。

本期不做：独立移动站、PWA、小程序、前端框架迁移、后端/API/数据库/ES 改造、离线草稿、手机全量配置后台。邮件模板编辑、AI 训练、批量发送配置、邮箱账号管理只保留入口，不承诺完成其全部移动端交互。查看任务不扩展为手机上的任务调度器。

## 关键不变量

- G-1：手机和桌面共用同一数据与业务动作；不复制发送表单、专家详情、筛选字段或任务轮询器。
- G-2：新增布局规则仅在 ≤760px 生效；跨断点不发送业务写请求，不清空草稿、不改选中专家和回复账号。
- G-3：产品按钮“返回列表”只改变呈现状态，不使用浏览器 history 模拟路由；系统返回键维持既有行为。本期不承诺浏览器返回键等同于产品返回按钮。
- G-4：三个子计划顺序执行，每个基于前一个通过验证的产物；共享 `index.html`、`app.js`、`styles.css` 不并行改写。（来源：K-master-plan-shared-file-sequential-gates）
- G-5：每段独立 bump index 中全部 11 个现有版本化资源，资源数量和加载顺序不变。执行前按实际旧键反查测试；清单外新增命中须先更新计划。（来源：K-frontend-cache-key-triad）
- G-6：既有工作区包含其他任务修改；只提交本方案授权文件的相关差异，不覆盖或打包无关改动。

## 样式契约

权威 CSS、DOM 和组件复用位置分别写在三个子计划；不增加全局“通用响应式框架”。不新建 CSS/JS 资源，避免新增加载顺序及资源数量契约。新增手机 CSS 以独立注释块追加至 `styles.css` 文件末尾；不改旧样式块或历史证据文件。

主色 `#1e40af`、主文字 `#1e293b`、次级文字 `#475569`；沿用 `.button` 状态规则。手机主按钮高度 44px，输入字号 16px，页面内边距 12px。正文和日志允许换行；只有明确的表格/月历容器允许横向滚动，不通过 `body{overflow-x:hidden}` 掩盖溢出。

## 实现方案

### 方案比较

| 路线 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 仅补 CSS | 改得快 | 邮箱仍上下堆叠，草稿/返回体验没有解决 | 仅适合基础可看 |
| 原页面 + 手机呈现状态 | 复用业务与接口，核心操作顺手 | 需要状态与竞态验证 | 本方案采用 |
| 单独移动前端 | 完全独立设计 | 两套业务、权限及维护成本 | 本期不采用 |

### 顺序与交付

| 顺序 | 子计划 | 用户可见结果 | 估算 |
|---|---|---|---|
| 1 | [01 导航与专家](mobile-core-01-shell-contacts.md) | 下拉切换页面；搜索专家→详情→原列表 | 1.5–2 人天 |
| 2 | [02 邮箱与回复](mobile-core-02-mailbox.md) | 会话独占屏幕；返回保草稿、位置；可回复和上传附件 | 2–3 人天 |
| 3 | [03 会议与任务](mobile-core-03-calendar-tasks.md) | 手机默认排期列表；任务卡片、历史与日志可读 | 1–1.5 人天 |
| 收尾 | 跨模块、真实设备与桌面回归 | 查专家→回信→查看会议/任务完整闭环 | 0.5–1.5 人天 |

合计 5–8 人天（熟悉项目的一名开发者，含验证；不是承诺的日历交付日期）。本次仅静态审计，先做首轮浏览器基线；若发现未覆盖的核心浮层或原有阻断性故障，先记录实际问题与范围差异再调整估算，不顺带全面重构。

每段可独立部署、验证和回滚。中间版本只宣称完成该段，不宣称全部手机核心流程完成。阶段机器验证通过后才进入下一段；完整功能验收通过后才建议统一上线。

## 验收标准

- G-1/G-2：手机与桌面相同操作的 API 路径、方法、payload 对照一致；纯导航/返回/旋转不产生业务写请求。
- G-3：手机返回按钮恢复列表上下文；不新增 popstate/pushState 路由。
- G-4/G-6：逐段保存基线、差异、命令、截图、未完成项；提交边界不包含既有无关修改。
- G-5：所有版本化资源同键，按键反查无漏改；原资源次序和数量未变。
- 子计划 I-n/S-n 全部通过。每段执行 `node --check` 对应 JS、针对性 node 测试及全量 `node --test src/test/js/*.test.js`。已有失败单独保存基线，新增失败不能标成既有失败；verify.sh只覆盖一个旧用例，不作前端门禁。（来源：K-js-test-invocation-surface）
- 真实浏览器在 360×800、390×844、430×932、768×1024、1024×768、1440×900 检查；额外覆盖 760/761、1024/1025 和横竖屏切换。视口宽度不等于真实触屏/软键盘，至少分别使用一部 iPhone Safari 与 Android Chrome 验证回复输入和上传。
- 核心页 `document.documentElement.scrollWidth <= clientWidth + 1`；局部横滑容器例外仅限专家表格、任务历史、月历、原始日志。例外容器仍必须限制在视口内。
- 浏览器自动化如无可用运行环境，不在方案阶段安装依赖；实施时可用现有浏览器工具完成检查。真实设备暂不可用时标为“待设备验收”，不宣称全部完成。

### A-1：完整核心闭环
- 前置条件：测试环境账号；后台已有两名测试专家 A/B、A 的一封待回复来信、A 的一条排期及两条有日志的任务记录；外发接收者为自有测试邮箱。
- 操作：390px 宽登录→页面选择“专家列表”→姓名查询 A→查看联系详情→进入 A 收发件箱→写入 `手机验收-20261003`→返回列表→再次进入 A→上传测试 PDF→发送→切会议查看 A 排期→切任务查看状态和日志。
- 预期：全程不用缩放；草稿仍为上述文本，收件人为 A；发送动作产生一次提交、测试邮箱只收到一封；排期显示北京时间；任务状态与桌面相同。

### A-2：桌面回归
- 前置条件：1440px 宽，专家分栏预先拖成 620px；保留登录会话。
- 操作：执行查询、查看详情、写草稿；切至390px再回1440px；刷新；查看会议月视图和任务；退出登录。
- 预期：桌面分栏仍为620px（在容器允许范围内）；详情/邮箱仍为分栏；原导航10入口和退出入口可用；未发送草稿不因旋转丢失；退出后鉴权行为同原版本。
- 覆盖：G-1/G-2、桌面/登录/个人偏好不变。

### A-3：真实设备与视觉
- 前置条件：测试环境；iPhone Safari、Android Chrome；各记录设备、系统和浏览器版本。
- 操作：打开回复编辑器唤起键盘；粘贴长邮件、长网址；上传文件；展开筛选、模板参考、会议弹窗；横竖屏切换；对照桌面截图。
- 预期：输入区与发送按钮均可通过正常滚动触达；无被键盘永久遮住的关闭/提交入口；核心触控按钮高度44px、输入字号16px、页面边距12px；正文不撑宽页面；浮层文本不透底。
- 覆盖：全部 S-n、G-2；设备受限时本项保持未通过。
