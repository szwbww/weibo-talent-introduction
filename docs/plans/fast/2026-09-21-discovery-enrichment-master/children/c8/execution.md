### Deviations

1. **`ExpertDiscoveryController.kt` intentionally unchanged** (authorized but not required). The new scope travels through the existing `@RequestParam(required = false) scope: EnrichmentScope?` binding, and the "stats 响应附加计数" are produced by the service's `EnrichmentStats`, which the existing `/enrich/stats` entry already returns verbatim. Touching the controller was additionally avoided because its constructor is referenced by the unauthorized `ExpertDiscoveryControllerMvcTest`. Regression evidence for the new behaviour lives in the controller test (`enrichExperts forwards DISCOVERY_PENDING scope to service`, `getEnrichmentStats carries the per-source counters of the last auto enrichment batch`).
2. **Enqueue-failure handling is "record + retain page", not "propagate a DB exception"** (I-1's "数据库错误向源抛可重试失败，02保留页"). It is surfaced at the source-run boundary exactly like the existing RAW-write failure: a count (`ENRICHMENT_ENQUEUE_FAILED`) + a dedicated stop reason (`DiscoveryStopReason.ENQUEUE_INCOMPLETE`), the entering cursor retained, `pendingWork = true` so the run ends `PARTIAL_SUCCESS`, and the replay path rebuilds the missing job from the matched `_id`. Propagating the exception would instead fail the whole discovery run (including healthy sources) and contradict master I-5's "部分失败为PARTIAL_SUCCESS". No exception is swallowed: it is logged with the doc id and the source.
3. **New additive stop reason `ENQUEUE_INCOMPLETE`** and reason code `ENRICHMENT_ENQUEUE_FAILED`. Master I-1 requires each stop to report its own reason; reusing `RAW_WRITE_INCOMPLETE` would conflate two different persistence gaps. Existing reasons/values are unchanged.
4. **`DISCOVERY_PENDING` = claim + process the due queue now.** It covers `PENDING`, due `RETRY_WAIT` (transient-failure backoff, rate-limit and quota deferrals) and expired-lease `RUNNING` — i.e. explicitly retrying the automatic tasks, which is what the plan states the scope is for ("用于明确重试自动任务"). **Recorded limitation:** reopening `FAILED` / `UNMATCHED` rows by id (`ExpertAcademicEnrichmentJobService.reopenFailed`, and the `enqueue` reopen for `UNMATCHED`) cannot be driven from this scope, because that requires enumerating those rows and c7 exposes no such read API; adding one would mean editing `ExpertAcademicEnrichmentJobRepository`/`…JobService`, which are outside this child's authorized file set. The automatic-recovery path that *is* exercised is 07's re-claim of due `RETRY_WAIT`/expired `RUNNING` (and the `UNMATCHED` reopen that any later discovery replay triggers through `enqueue`). The three legacy scopes are untouched.
5. **Claim and process are two service entry points** (`claimDueEnrichmentJobs` + `processClaimedEnrichmentJobBatch`) instead of one `process(batchSize)`. Rationale: the worker checks every 30 s, and a single "claim inside the task record" shape would write an empty `EXPERT_ENRICHMENT` task record (and progress-log row) on every idle check — 2 880 rows/day of pure noise, which also breaks the A-1 acceptance expectation of exactly the 100+1 batches landing in the task list. The idle check therefore produces no task record and no progress log; the manual entry writes one honest "没有到期任务 / OpenAlex 未启用，本轮未领取任何任务" progress entry per operator click.
6. **OpenAlex provider absent ⇒ nothing is claimed** (and no progress log for automatic checks). This mirrors the existing manual-entry behaviour ("OpenAlex 未启用，跳过补充") and prevents 07's 5-attempt failure budget from being burned by a configuration state (06 maps "provider absent" to `RetryableError`, which would otherwise degrade every job to `FAILED` within ~2.6 h).
7. **RAW profile loading:** if the batch's claimed documents cannot be read at all (`findByDocumentIds` throws, or every doc is missing — index/mapping/ES fault), the batch throws before writing any task state; the claimed rows stay `RUNNING` and are re-claimed after their lease expires, so an infrastructure fault never consumes a job's retry budget (the worker records the batch as `FAILED`). A *single* unreadable doc inside an otherwise healthy batch is completed as `RetryableError` (bounded by 07's 5-attempt budget) rather than silently skipped, so a claimed row can never be left cycling on its lease forever.
8. **`renewLease` is not called by the worker.** One batch is one `enrichProfiles` call (≤2 identity chunks × ≤2 requests for base facts, bounded by 15 s read timeouts) — far below 07's 10-minute lease — and the lease remains the crash safety net; renewing ≤100 rows per tick would add DB writes with no behavioural benefit. Recorded because 07's job-service doc mentions "worker每批续租" as an available affordance.
9. **`EnrichmentStats` gained one additive, defaulted field** (`autoEnrichment: AutoEnrichmentBatchResult? = null`). The plan explicitly asks for "stats 响应附加计数"; the field is response-only (no DB column, no ES mapping, no frontend change — `app.js` reads only `stats.enrichedLast30d`), it is documented as a process-local observation of the last batch, and the job table remains the only lifecycle fact. It is populated by both the automatic worker and the manual `DISCOVERY_PENDING` entry (same core).
10. **Email dedup now sends `size: 1` + `_source: false`** (was `size: 0`). Hit detection is still `hits.total.value`; the hit body is only used to read the matched document's real `_id` for the replay rebuild. When a response reports `total > 0` without a readable hit `_id` (the shape produced by the shared test helper `DiscoveryMockHelper.stubEsDedupSearch`), the run still counts the duplicate but creates no job — the same behaviour those pre-existing tests assert; production ES always returns a hit for `size: 1`.
11. **Worker gating**: `@ConditionalOnProperty(prefix = "talent-introduction.scheduling", name = ["enabled"], havingValue = "true")` (parity with `MailAutomationScheduler`) plus the separate feature switch that defaults to false. With scheduling enabled but the switch off the bean still exists and simply returns; with the switch on the batch work still leaves the shared scheduler thread immediately.
12. `processPaper` (pre-existing, no callers) was updated only to keep the `consumeOutcome` signature consistent; it remains uncalled.
