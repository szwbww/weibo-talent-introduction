## 判定方法

1. 仅查询 `tags=discovered`，取真实 `_id`、邮箱、姓名、身份凭证、externalIds 和层级。每层 scroll 的实际条数与 total 一致；三层顺序快照，不声称跨索引事务快照。
2. 按真实 `_id` 合并层级副本。相同 ID 的身份/凭证/来源作者编号不一致会标记，不能进入高置信组。
3. 按规范 ORCID/OpenAlex 作者编号连成候选组；要求组内至少两个不同邮箱。业务键形如 ORCID 仅为候选线索，不能单独作为高置信证明。
4. 高置信组要求所有档案：身份 status=VERIFIED、version=20260925、证据摘要格式有效、凭证姓名邮箱与当前档案一致，且凭证携带可信作者编号；组内标准化全名相同，每类作者编号最多一个，凭证与 externalIds 无冲突，层间无身份冲突。姓名只作一致性检查，不单独决定合并。
5. 此结论基于现有库存凭证，**没有本轮逐组重新查询公开原文**；应称“高置信合并候选”，不能称全部已完成源头复核或已经合并。合并前仍需检查联系人、人工决定、邮箱别名及历史引用。

高置信档案按来源：ORCID 7,885，OPENALEX 537，CROSSREF 4。高置信组邮箱数：2 个 2,981 组；3 个 624 组；4 个 107 组；5 个 17 组；6 个 7 组；7 个 4 组；9 个 1 组。

161 个待核组的原因可交叉：缺有效绑定作者凭证 107 组，姓名变化/冲突 48 组，多 ORCID 61 组，多 OpenAlex 作者 ID 27 组。原因数不能相加当组数。

此外，仅按同名不同邮箱可找到 4,645 组、10,802 条，包含上表重叠记录及可能同名不同人，未计入高置信合并量；同邮箱不同业务 ID 另有 1 组 2 条，属于另一种重复现象。

## 纳入后续修复的需求边界

1. **一个人一份主档，多邮箱作为该人的联系方式**，每个邮箱保留独立来源、验证、抑制和使用状态；新增发现同一可靠身份时归入既有人，不再按邮箱增加一个人物展示。
2. 人物聚合只依据可靠作者身份及一致来源；同名、同机构、邮箱拼写相似不自动合并。161 个待核组保持分开，先补证/消除冲突。
3. **同一首发任务按人去重**，只选一个符合原准入与邮箱条件的地址；合并不能导致同人多个邮箱被逐一首次邀请。邮件历史保持原 ID/邮箱，展示通过主档关系汇总，不能覆盖原记录。
4. 现有 `expert_email_alias` 属于已建联系人，外键指向 expert_contact，并不是采集阶段的人物主档；不能通过为每位未联系专家创建联系人来冒充完成合并。V148 准入绑定原 docId/姓名/邮箱，V23 发信占位也按原业务键，须分阶段设计其关联与并发去重，不能只删除 ES 副本。
5. 本轮合并目标严格限定已冻结的 discovered ID。发现组成员关联了其他范围档案时列为跨范围冲突，本轮不修改那些档案；当前待确认 10,686 清单不并入本次目标。联系人、邮件及别名只作为历史保护检查。
6. 已据本次名单补入 [总计划的 04—10 子计划](../../plans/2026-10-13/discovery-identity-recovery-master.md)：人物主档、后续发现归人、列表与详情、发送目标与原子防重、历史合并。本节仍只是数据依据，计划尚未实施，不构成生产迁移或发信授权。
